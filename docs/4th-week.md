## 1. Назначение и задачи проекта

### 1.1. Общая характеристика

«Магазин чая» — учебный проект интернет-магазина, ориентированного на продажу чая с разделением действий между гостем, покупателем и администратором. Система объединяет каталог товаров, регистрацию пользователей, корзину, адреса доставки и оформление заказов. Предметная область — продажа конкретных сортов чая с удобным каталогом и единым процессом покупки.

Цель проекта — разработать серверную основу сервиса, обеспечивающую работу с ассортиментом, учёт пользователей и последовательный процесс покупки.

### 1.2. Основные задачи

- Реализовать регистрацию и вход с разграничением доступа по ролям.
- Организовать каталог, категории, поиск, фильтрацию и управление товарами.
- Предусмотреть корзину, сохранение адресов доставки и оформление заказа.
- Обеспечить хранение данных в PostgreSQL и доступ к ним через REST API.
- Добавить валидацию запросов, защиту данных пользователей и автоматизированные проверки.

### 1.3. Роли пользователей

| Роль | Предусмотренные возможности |
|---|---|
| Гость | Просмотр каталога, карточек товаров и категорий. |
| Пользователь | Регистрация, вход, работа с корзиной, адресами и заказами. |
| Администратор | Создание, изменение и удаление товаров и категорий; изменение статуса заказа. |

Область подтверждённой реализации: в архиве доступны исходники backend, миграции, тесты и проектная документация. Описание визуальных экранов ниже основано на документации и функциях API; готовность клиентского интерфейса по этому архиву подтвердить нельзя.

### 1.4. Ролевая модель и права доступа

В документации описаны три уровня доступа: гость, покупатель и администратор. Авторизованный покупатель управляет собственными данными, а административные операции дополнительно проверяются на сервере.

| Действие | Гость | Покупатель | Администратор |
|---|:---:|:---:|:---:|
| Каталог и карточки товаров | Да | Да | Да |
| Поиск и фильтры | Да | Да | Да |
| Личный профиль | — | Да | Да |
| Корзина и адреса | — | Да | Да |
| Оформление и история заказов | — | Да | Да |
| Создание и изменение товаров | — | — | Да |
| Управление категориями | — | — | Да |
| Изменение статусов заказов | — | — | Да |

Поле `role` технически допускает значение `seller`, но отдельная проверка полномочий продавца в текущем API не реализована: для административных маршрутов требуется `role=admin`.

### 1.5. Основной пользовательский сценарий

Пользователь знакомится с каталогом, переходит к карточке товара и добавляет выбранные позиции в корзину. После авторизации он выбирает адрес доставки и оформляет заказ. В личном кабинете доступны история и подробности покупок.

Администратор управляет товарами и категориями, а также обрабатывает заказы. Обобщение пользовательских действий приведено на исходной диаграмме прецедентов в следующем подразделе.

## 3. Организация базы данных

В приложении описаны семь основных таблиц. Связи между ними представлены средствами SQLAlchemy; создание и изменение структуры БД выполняется через Alembic.

| Таблица | Назначение и основные поля |
|---|---|
| `users` | Учётные записи: email, имя, хеш пароля, роль. |
| `categories` | Категории продукции: название, slug, описание. |
| `products` | Товары: категория, название, цена, вес, остаток, происхождение, изображение. |
| `cart_items` | Позиции корзины: пользователь, товар, количество. |
| `addresses` | Адреса доставки: пользователь, город, улица, дом и прочие реквизиты. |
| `orders` | Заказы: пользователь, адрес, статус, общая сумма, способ оплаты. |
| `order_items` | Состав заказа: товар, количество и цена на момент покупки. |

### 3.1. Ключевые связи

- Один пользователь может иметь несколько адресов, позиций корзины и заказов.
- Каждый товар относится к одной категории; одна категория объединяет несколько товаров.
- Один заказ содержит несколько товарных позиций, которые хранят цену покупки.

### 3.2. Контроль целостности

Для товаров предусмотрены ограничения положительной цены и веса, а также неотрицательного складского остатка. Для позиций корзины и заказа количество должно быть положительным. При оформлении заказа сервер повторно проверяет наличие товара и сохраняет итоговую сумму.

Цена в `order_items` фиксируется в поле `price_at_purchase`. Это позволяет хранить цену товара на момент оформления заказа, независимо от последующих изменений каталога.

### 3.3. Исходная диаграмма модели данных

На первоначальной диаграмме отражены основные сущности предметной области: пользователи, адреса, товары, категории, корзина и заказы. Диаграмма взята из проектных материалов и приведена без изменения её структуры.

## 4. Основные функции и API

Сервер предоставляет REST API с префиксом `/api`. Ниже приведены ключевые группы маршрутов, которые используются для работы магазина.

| Раздел | Основные маршруты | Операции |
|---|---|---|
| Авторизация | `/api/auth/register`, `/login`, `/refresh`, `/me` | Регистрация, вход, токены, профиль. |
| Каталог | `/api/categories`, `/api/products` | Списки, карточки, поиск, фильтры, CRUD администратора. |
| Корзина | `/api/cart`, `/api/cart/items` | Просмотр, добавление, изменение, удаление. |
| Адреса | `/api/addresses` | Создание, список, изменение, удаление. |
| Заказы | `/api/orders` | Оформление, история, детали, смена статуса. |
| Сервис | `/health`, `/db-check`, `/docs` | Проверки работоспособности, Swagger UI. |

### 4.1. Поиск товаров

Каталог поддерживает фильтрацию по категории и цене, поиск по названию и описанию, сортировку, проверку наличия и постраничную выдачу. Ответ включает список позиций, общее число результатов и параметры страницы.

### 4.2. Сценарий оформления заказа

1. Пользователь входит в учётную запись и добавляет товар в корзину.
2. Выбирает сохранённый адрес и инициирует оформление заказа.
3. Сервер проверяет владельца адреса, содержимое корзины и складские остатки.
4. В транзакции создаёт заказ, фиксирует цены, уменьшает остатки и очищает корзину.
5. Созданный заказ становится доступен в истории пользователя.

## 5. Безопасность и тестирование

### 5.1. Авторизация и контроль доступа

Пароли сохраняются в виде bcrypt-хешей. При успешном входе сервер выдаёт два JWT-токена: access-токен для выполнения запросов и refresh-токен для обновления сессии. По умолчанию время действия составляет 30 минут и 7 дней соответственно.

Запросы к персональным данным зависят от текущего пользователя. Доступ к чужому адресу, заказу или позиции корзины ограничивается проверкой владельца; для административных действий применяется зависимость проверки роли `admin`.

### 5.2. Организация тестов

В директории `backend/tests` находятся автоматизированные тесты HTTP-интерфейса. Они используют pytest, pytest-asyncio и httpx, а тестовые запросы направляются к ASGI-приложению.

| Файл тестов | Проверяемая область |
|---|---|
| `test_auth.py` | Регистрация, вход и токены. |
| `test_categories.py` | Операции с категориями и права доступа. |
| `test_products.py` | Каталог, CRUD, фильтры и пагинация. |
| `test_cart.py` | Изменение корзины и ограничения по количеству. |
| `test_orders.py` | Создание заказов, остатки и статусы. |
| `test_isolation.py` | Ограничения доступа к данным других пользователей. |

Наличие тестовых файлов подтверждено исходным кодом. Результаты полного запуска pytest в рамках подготовки настоящего отчёта не заявляются: тестовому окружению требуется настроенная PostgreSQL.

## 6. Запуск и демонстрация

### 6.1. Подготовка окружения

Для запуска необходимы Python, PostgreSQL и установленные зависимости из `requirements.txt`. Конфигурация соединения с базой и ключ подписи JWT задаются в файле `.env` на основе `.env.example`.

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
python -m app.data.demo_data
uvicorn app.main:app --reload
```

До применения миграций требуется создать PostgreSQL-базу, указанную в `DATABASE_URL`. Команда загрузки демо-данных необязательна и нужна для заполнения каталога тестовым содержимым.

### 6.2. Проверка работы сервера

| Адрес | Назначение |
|---|---|
| `http://localhost:8000/docs` | Интерактивная документация Swagger UI. |
| `http://localhost:8000/redoc` | Альтернативное представление схемы API. |
| `http://localhost:8000/health` | Состояние HTTP-сервиса. |
| `http://localhost:8000/db-check` | Простая проверка обращения к PostgreSQL. |

### 6.3. Порядок демонстрации

Рекомендуется последовательно показать каталог, вход и регистрацию, работу с корзиной и адресами, оформление заказа, его появление в истории, а затем административные действия. Если визуальный интерфейс недоступен, соответствующие операции можно представить в Swagger UI.

## 8. Заключение

В рамках учебного проекта «Магазин чая» разработана серверная часть интернет-магазина. Она включает учётные записи пользователей, каталог и категории, операции с корзиной, адреса доставки и создание заказов. Данные представлены реляционными моделями и обрабатываются через HTTP API.

В проекте предусмотрены меры защиты: хеширование паролей, JWT-авторизация, разграничение административных прав и изоляция пользовательских объектов. Структура базы управляется миграциями, а для основных операций подготовлены автоматизированные тесты.

Для полноценной демонстрации работы системы следует развернуть базу данных и сервер, подключить клиентский интерфейс, а затем заполнить отведённые в разделе 7 поля скриншотами соответствующих экранов. Если готового фронтенда нет, работу функций можно подтвердить интерактивными запросами в Swagger UI.
